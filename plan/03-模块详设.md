## ① 采集器 `collectors`

### 输入

```
certledger collect --roots <path>... [--files <path>...] [--source auto|linux|windows|macos|none]
                   [--follow-symlinks] [--max-size <bytes>]
```

- `--roots` 可多次；`--files` 可多次；两者至少给一个，否则退出码 2。
- `--source` 默认 `auto`：按平台探测，失败降级为 `SOURCE_UNAVAILABLE`（不失败）。
- `--follow-symlinks` 默认关闭（防环、防越界）；打开时记录一条 INFO 说明。
- `--max-size` 来自策略（`collect.max_file_bytes`），命令行可覆盖。

### 输出（候选流）

| 字段 | 说明 |
|---|---|
| `path` | 规范化路径（大小写归一 + Unicode NFC）；报告层按 `--no-redact` 决定是否打码 |
| `offset` | PEM 多块文件内的块序号（0 起）；非 PEM 为 0 |
| `detected_format` | `pem-cert` / `pem-key` / `pem-pkcs7` / `der-cert` / `pkcs7` / `pkcs12` / `jks` / `jceks` / `pkcs8` / `openssh-pub` / `unknown` |
| `container_alias` | 容器内 alias（非容器为 null） |
| `file_sha256` | 整个文件的 SHA-256（用于"同一文件被多次扫到"的去重与审计） |
| `parse_status` | `ok` / `PARSE_FAILED` / `PARSE_UNSUPPORTED` / `SKIP_*` |

### 嗅探策略（按内容，不按扩展名）

- 读固定前缀窗口 `collect.sniff_bytes`（策略常量，默认 4096）：
  1. 以 `-----BEGIN ` 开头 → PEM，按 RFC 7468 label 分类；多块文件逐块展开；
  2. 首字节 `0x30` 且长度合理 → 尝试 DER 解析；解析出 X.509 → `der-cert`；
     PKCS#7 `ContentInfo` OID → `pkcs7`；
  3. `0xFE 0xED 0xFE 0xED` → JKS；`0xCE 0xCE 0xCE 0xCE` → JCEKS（**原文写"同魔数"是错的**，JDK 26 实测两者不同）；
  4. `ssh-rsa` / `ssh-ed25519` / `ecdsa-sha2-` 起始行 → `openssh-pub`；
  5. 其余 → `unknown`（**不报错**，记 `SKIP_UNKNOWN_FORMAT`）。

### 跳过原因码（一个都不能静默）

`SKIP_BINARY` / `SKIP_PERMISSION_DENIED` / `SKIP_TOO_LARGE` / `SKIP_SYMLINK` /
`SKIP_UNKNOWN_FORMAT` / `SKIP_UNREADABLE`。**六个**——原文的"五种"漏了 `SKIP_UNREADABLE`。

计数口径（`summary`，三者是**不同单位**，不可相加）：

| 字段 | 含义 |
|---|---|
| `visited` | 遍历看到的文件总数 |
| `scanned` | 打开并读完（或读到判定所需）的文件数 |
| `skipped` | **从未打开**的文件数（遍历期拒绝 + 读取失败） |
| `skip_records` | `SKIP_*` **诊断条数**（读到了、但内容不是证书也算一条） |
| `deduplicated` | 同一目录经另一路径二次到达的次数（联结/绑定挂载/重叠 `--roots`） |

恒等式 `visited == scanned + skipped` 由构造保证，并有测试断言。
`skip_records` 单独一列，是因为"读到了但不是证书"和"根本没读"必须能分开——
把它们并进 `skipped` 会把恒等式打破，也正好抹掉这个区分。

### 后端（`--source`）

| 后端 | 读取方式 | 缺失时 |
|---|---|---|
| linux | `/etc/ssl/certs/ca-certificates.crt`（PEM bundle），按 Debian/Fedora/openSUSE/Alpine 顺序探测 | `SOURCE_UNAVAILABLE` |
| windows | `certutil -split -store <Root\|AuthRoot\|CA>`：每个证书落一个 DER 文件，取**原始 DER**（D5；**不用** `storeutl winstore`，也不解析本地化控制台文本） | `SOURCE_UNAVAILABLE` |
| macos | `security find-certificate` | **未实测（D4）** → 一律 `SOURCE_UNAVAILABLE` 并标 `unverified_backend: true` |
| none | 不探测 | — |

### 断言基准（M2）

- 八类格式各一样例能被识别（`tests/test_collectors.py`）；
- 目录含不可读文件时：产 `SKIP_PERMISSION_DENIED`、退出码 0；
- 后端缺失：产 `SOURCE_UNAVAILABLE`、退出码 0、报告里可检索到后端名与失败原因；
- 遍历顺序稳定：同一目录树两次运行，候选流**列表相等**（不是集合相等）；
- 循环符号链接 + `--follow-symlinks` 关闭 → 不递归、记 `SKIP_SYMLINK`。

> **M2 实测补齐（2026-10-21）**——下面三处是原文写错或不完整的地方，已按实测改正：
>
> 1. **JCEKS 魔数是 `CE CE CE CE`，不是与 JKS 共享 `FEEDFEED`。** JDK 26 `keytool` 建库实测：
>    JKS 头 `feedfeed`、JCEKS 头 `cececece`。原文"JCEKS 同魔数，靠 keytool 判定"会让每个
>    JCEKS 被标成 JKS，`CONTAINER_FORMAT_AMBIGUOUS` 也因此没有存在必要（已从代码移除）。
> 2. **跳过原因码实际有六个**：原文列五个，漏了 `SKIP_UNREADABLE`（文件存在但读不出、
>    不是普通文件、或显式给出的路径不存在）。六个全部有测试覆盖。
> 3. **`file_sha256` 与"只读前缀窗口"的关系**：分类只读 `collect.sniff_bytes` 前缀；
>    一旦前缀判定为证书/密钥/容器结构，为算 `file_sha256` 必须读完整文件。因此
>    "不整文件读"成立的对象是**未识别的文件**（占真实目录树的绝大多数），不是全部文件。
>
> 另补两条实测得来的判据：
>
> - **`0x30` 也是 ASCII `'0'`**：校验和文件、git reflog、带时间戳的日志都以它开头。嗅探必须先判
>   "是否文本"再进 ASN.1，否则普通文本会被报成 `PARSE_FAILED`，甚至因 ASN.1 偶然走得通而误标成容器。
> - **Windows 的 `certutil -store Root` 只列物理 Root 配置单元（18 张）**，而
>   `Cert:\LocalMachine\Root` 视图是 76 张（= Root 18 + AuthRoot 58，含 4 张重叠）。
>   只读 Root 会静默漏报。后端因此读 `Root`/`AuthRoot`/`CA`，并**分别报告各自计数**。

## ② 归一化台账 `inventory`

### 记录模型（`model.py` 是唯一真值结构）

```jsonc
{
  "schema_version": 1,
  "certs": [
    {
      "fingerprint_sha256": "…",      // 证书 DER 的 SHA-256（K1）
      "spki_sha256": "…",             // SubjectPublicKeyInfo DER 的 SHA-256（K4）
      "subject": {"display": "…", "der_sha256": "…"},
      "issuer":  {"display": "…", "der_sha256": "…"},
      "san": {"dns": [], "ip": [], "email": [], "uri": []},
      "not_before": "2049-01-01T00:00:00Z",
      "not_after":  "2050-01-01T00:00:00Z",
      "key_algo": "rsa|ec|ed25519|…",
      "key_bits": 2048,
      "curve": null,
      "sig_algo": "sha256WithRSAEncryption",
      "key_usage": ["digitalSignature"],
      "extended_key_usage": ["serverAuth"],
      "is_ca": false,
      "subject_key_id": "…",
      "sources": [ {"kind":"file|container|store","path":"…","container_format":null,"alias":null,"entry_type":null,"store_name":null} ]
    }
  ],
  "keys": [
    {"spki_sha256":"…","key_algo":"rsa","key_bits":2048,"curve":null,
     "encrypted":false,"paired_cert_fingerprint":"…","sources":[...]}
  ],
  "diagnostics": [
    {"code":"PARSE_FAILED|SOURCE_UNAVAILABLE|SKIP_*|CONTAINER_UNREADABLE","path":"…","stage":"…","detail":"…"}
  ]
}
```

### 合并与配对（分水岭）

- **同一 `fingerprint_sha256` → 一条记录**，多个来源进 `sources[]`；同一 `spki_sha256` 的私钥同理。
- `sources[]` 按 `(kind, path, alias)` 稳定排序；键序固定（不靠 `sort_keys`）。
- 配对：证书 `spki_sha256` == 私钥 `spki_sha256` → `paired_cert_fingerprint` 回填。
  同 CN 不同密钥对**必须不配对**（SPKI 不同）；同证书多副本**不影响**配对。
- **禁止**：按文件名（`server.crt`）、subject/CN、SKI 配对（K4）。

### 失败路径

| 情形 | 记录 | 退出码 |
|---|---|---|
| DER 结构损坏 | `PARSE_FAILED`（`path` + `stage=der`） | 0 |
| PEM 块 base64 损坏 | `PARSE_FAILED`（`stage=base64`, `offset`） | 0 |
| 加密私钥无口令 | `key` 记录 `encrypted=true`、`spki_sha256=null` | 0 |
| 容器内条目无法解密 | `CONTAINER_UNREADABLE` | 0 |

### 断言基准（M3）

- 同一张证书放在 3 个目录 → `certs` 长度 1、`sources` 长度 3；
- 同 CN 不同密钥对两张证书 → 2 条记录、均不配对；
- 证书 + 对应私钥 → `paired_cert_fingerprint` 指向正确指纹；
- JSON 两次运行字节级一致（同 `--as-of`）。

> **M3 实测补齐（2026-10-21）**——三处原文未写、但会改变结果的事实：
>
> 1. **`subject` / `issuer` 的 `der_sha256` 取自 TBS 字段切片**，不是
>    `Name.public_bytes()`。两者在 20 张夹具 + 81 张真实 Windows 存储证书上逐字节相等，
>    但"今天恰好相等"不是 K1 的契约；切片入口是 `parsing/x509.py`，只认 RFC 5280 §4.1 的字段序。
> 2. **v1 证书的 `TBSCertificate` 只有 6 个字段**（没有 `[0] version`）。按"≥7"守卫会
>    静默丢掉 issuer/subject 哈希——本机 3 张 1997 年 v1 根证书就是这么丢的。
> 3. **81 张真实存储证书里有 1 张 `cryptography` 解不出公钥**（`CN=Root Agency`，MD5 签发）。
>    它的 SPKI 切片完好，指纹与 `spki_sha256` 都正确，只有 `key_algo` / `key_bits` 为空。
>    **记录必须保留**：丢掉它等于台账少一张证书。
>
> 另：**未展开的容器**（PKCS#12/JKS/JCEKS）产一条 `PARSE_UNSUPPORTED`
> （`stage=container`）。原文只说"容器内条目无法解密 → `CONTAINER_UNREADABLE`"，
> 没有覆盖"这一版根本不展开容器"的情形；不产记录会让台账看起来像"容器里没有证书"。

## ③ 卫生规则 `hygiene`

### 输入

归一化台账 + 策略文件 + `--as-of`。**`--as-of` 缺失 → 退出码 2**（不给默认值，K2）。

### 输出

```jsonc
{"code":"EXPIRED","severity":"ERROR","subject":"CN=…","fingerprint":"…",
 "evidence":{"not_after":"…","as_of":"…","days_over":12},
 "rule_source":"RFC 5280 §4.1.2.5"}
```

### 规则表（九项，逐条给出处；阈值全在策略文件）

| # | code | 判据 | 难度 | 出处 |
|---|---|---|---|---|
| 1 | `EXPIRED` / `EXPIRING` | `not_after < as_of` / `[as_of, as_of+warn_days)` | ERROR / WARN | RFC 5280 §4.1.2.5；`data/README` §五.2 |
| 2 | `EXPIRY_CLIFF` | 窗口内**去重证书数** ≥ `cliff_min_count` | WARN | 本工具定义（`data/README` §五.3） |
| 3 | `WEAK_KEY` | RSA `bits < 2048`；EC 曲线 ∉ {P-256,P-384,P-521} | WARN（可升 ERROR） | CA/B TLS BR v2.3.1 §6.1.5；NIST SP 800-131A Rev.2 |
| 4 | `WEAK_SIG` | `sig_algo` 含 SHA-1 | WARN | NIST SP 800-131A Rev.2 |
| 5 | `POLICY_NIST_2031` | RSA 2048 且策略启用 2031 档 | INFO | SP 800-57 Pt1r5 表 2/表 4；800-131A Rev.2 §1.1 |
| 6 | `PRIVATE_KEY_UNENCRYPTED` / `PERMISSION_TOO_OPEN` | 可无口令解析 / POSIX mode 含 `o+r`\|`g+r` | WARN | 本工具定义（`data/README` §五.5）；D3 纪律见下 |
| 7 | `ORPHAN_CERT` / `ORPHAN_KEY` | `spki_sha256` 无对应私钥 / 无对应证书 | INFO | 本工具定义（§五.6） |
| 8 | `DUPLICATE_CERT` / `DUPLICATE_KEY` | 同指纹 `sources` 长度 > 1 | INFO | §五.7 |
| 9 | `CONTAINER_TRUSTSTORE_WITH_KEY` / `CONTAINER_EMPTY_PASSWORD` | 容器级信号（M5 供数） | WARN / INFO | 本工具定义 |
| 10 | `PUBLIC_VALIDITY_HINT` | 公网有效期政策 200/100/47 天 | INFO（**不参与合规判定**） | CA/B BR §6.3.2 时间表 |

补充：`SOURCE_UNAVAILABLE` / `PARSE_FAILED` / `CONTAINER_UNREADABLE` 也必须作为 finding 出现在报告里
（否则"没找到"与"没看"无法区分）。

### 纪律

- 每条 finding **必须**有 `rule_source`；**无出处的判据不得进入规则集**（`tests/test_strength.py`
  断言 `rule_source` 非空且匹配 `RFC|CA/B|NIST` 或 `本项目定义`+`data/README` 节号）。
- 默认 `WARN`，策略可升 `ERROR`，可 `off`（`level: off` 时**不产 finding**，但仍计数进 `summary.suppressed`）。
- **禁止**"RSA 2048 现在已弱"表述；`POLICY_NIST_2031` 文案固定为"按 NIST 时间表，2031 年起不再允许用于施加保护"。
- **统计口径**：`summary` 里同时给 `records`（台账条数）与 `findings`（finding 条数），
  两者是不同单位，恒等式写成"每条 finding 至少引用一条记录"（集合划分，不是相等）。

### 过期表

`not_after` 升序，`--top N` 只影响**展示**；不裁剪 finding 全集、不影响退出码（截断门禁 = CI 后门）。

> **M4 实测补齐（2026-10-21）**——原文未写、但会改变结论的五点：
>
> 1. **`sig_algo` 存的是 dotted OID，不是算法名。** 原文表格写"`sig_algo` 含 SHA-1"，
>    但 `ObjectIdentifier` 没有公开的 `.name`，只有私有的 `_name`（`inventory._stamp` 时已因此
>    改存 dotted）。`WEAK_SIG` 因此走 `_signature_name()`：查 `_name` 后与策略里的
>    `forbidden_digests`（`sha1` / `md5`）做子串比对；查不到名字就用 dotted 串，匹配不上任何
>    摘要名 → 不产 finding（**未知不等于弱**）。
> 2. **`level` 是每条规则一块，不是全局一个。** 策略文件的每个规则块都带自己的 `level`，
>    连"过期"也有（原文只在第 1 行写了 ERROR/WARN，容易被读成代码里的常量）。
>    校验器在加载时拒绝 `ERROR|WARN|INFO|off` 之外的取值——拼错的级别会静默沉到排序末尾、
>    永不被 `--fail-on` 碰到，那是"看起来跑过了"的失败。
> 3. **失败路径的级别存在 `hygiene.diagnostics.codes`**，逐码给定，未列出的码取同块 `default`。
>    采集器的码表是开放的（`SKIP_*` 会随遍历器增长），硬化成代码分支会让新码静默消失。
> 4. **`ORPHAN_*` 跳过 `spki_sha256 is None` 的加锁私钥**（原文没有这一条）。没有 SPKI
>    就没有配对依据，"查不了"不是"没有"。同理 `key_algo == ""` 不判 `WEAK_KEY`。
> 5. **容器三条规则消费台账的 `containers[]` 段**，由容器视图填充。该段缺席时规则不产
>    finding，容器本身仍以 `PARSE_UNSUPPORTED`（`stage=container`）可见——所以"容器没被打开"
>    在任何情况下都不会读成"容器里没有证书"。`containers[]` 的元素形状见下方 M5 约定。
>
> **台账新增字段**：`sources[].posix_mode`（八进制字符串，Windows 为 `null`）。
> 由采集器在读到文件的那一刻记录，之后不重读——台账可能在另一台机器上被 `hygiene` 消费。
>
> **`containers[]` 元素形状（M5 已填充，M4 已消费）**：
> ```jsonc
> {"path": "…", "format": "pkcs12|jks|jceks", "password": "set|empty|unknown",
>  "has_private_key": true,
>  "entries": [{"alias": "…", "entry_type": "privateKey|trustedCert|secretKey",
>               "fingerprint_sha256": "…", "spki_sha256": "…", "chain_length": 0,
>               "same_fingerprint_aliases": ["…"]}],
>  "unreadable": null}   // 读不了时给一句 reason，entries 为空（password 记 unknown）
> ```
> 规则只读 `path` / `password` / `has_private_key` / `entries[].entry_type` / `unreadable`；
> 其余列是给人与给交叉核对用的（M5 补）。**容器内容的归并**：容器里的证书/私钥进同一张
> `certs[]` / `keys[]`，`sources[].kind="container"` 且带 `container_format` / `alias` /
> `entry_type`；因此"未展开容器"的 `PARSE_UNSUPPORTED`（`stage=container`）在 M5 之后**只对
> PKCS#7 这类真正不读的格式保留**，读不开的容器改由 `unreadable` → `CONTAINER_UNREADABLE` 表达。
> 容器内的私钥记 `encrypted: true`：它在容器里受容器口令保护，不产 `PRIVATE_KEY_UNENCRYPTED`。

## ④ 报告与门禁 `report`

### 输入 / 输出

```
certledger report --as-of <ts> [--json <path>] [--markdown <path>]
                  [--fail-on ERROR|WARN|INFO|none] [--baseline prev.json]
                  [--top N] [--no-redact] [--policy <path>]
```

- 报告头必须回显：`as_of`（原样）、`policy_version`、`policy_sha256`、`tool_version`、`schema_version`。
- `--baseline`：输出 `added[]` / `removed[]` / `rotated[]` 三类 diff。
  **轮换判定**：同 `subject` 且同 `spki_sha256` 但 `fingerprint_sha256` 不同 → 同一密钥重签；
  同 `subject` 且 `spki_sha256` 也不同 → 视为 `removed` + `added`（不叫轮换）。

### 退出码

见 `plan/02` §五 / `data/README` §五.8。`--fail-on none` 时恒 0（但仍输出 finding）。

### 确定性

- 排序：`severity → code → subject → fingerprint`；
- 同一输入 + 同一 `--as-of` 两次运行**字节级相同**（JSON 与 Markdown 都测）；
- 不嵌运行时间戳/耗时；绝对路径默认打码（`render/redact.py`，按路径**形态**判断而非前缀硬编码）。

### 渲染三律（M5 验收）

1. **渲染层零判定**：`render/` 不得 import `hygiene`；AST 守门测试断言。
2. **零外链**：Markdown 正文不得出现 `http(s)://`（`rule_source` 里的规范号是文本不是链接）。
   **证书名可能自带 URL**——真实信任库根证书的 subject 就是 `CN=http://www.usertrust.com`（M6
   干净环境复跑实录）；这类**数据**由渲染层把冒号转义成 `http\://`（人读仍是 `http://`，但既不成
   链接、也不触发本律）。缺这一步会让 `report --markdown` 在任何读过系统库的机器上抛错——
   数据不得被当成渲染层引入的外链（M6 修正）。
3. **多格式同源**：JSON 与 Markdown 由同一个内存模型渲染；Markdown 的表格行数 = `findings` 条数。

> **M5 实测补齐（2026-10-21）**——原文未写、但会改变结论的六点：
>
> 1. **编排在 `pipeline.report`，不在 `render/`。** `render/` 一旦自己调 `hygiene` 就违反了第一律，
>    所以分工是：`pipeline.report` 建台账 → 调 `hygiene.evaluate(ledger=…)` → 把 findings 文档
>    交给 `render.render(findings_document=…, ledger=…, …)`。**`hygiene.evaluate` 新增
>    `ledger=` 关键字**（内存台账），使一次 `report` 只读机器**一次**；同给 `--inventory`/`--roots`
>    会报"台账来源冲突"（一份台账只能描述一台机器）。
> 2. **报告文档形状**（键序即 schema 序）：
>    `{schema_version, kind:"report", tool_version, as_of, as_of_utc, policy_version,
>    policy_sha256, fail_on, exit_code, summary{records,findings,by_severity,suppressed,
>    suppressed_by_code,certificates,expiries_total,expiries_shown}, certificates[],
>    findings[], expiries[], diff?}`。`certificates[]` = `{fingerprint_sha256, spki_sha256,
>    subject, subject_der_sha256}`，是 **baseline 的输入**：轮换判定要 SPKI，而 SPKI 不在任何 finding 里。
> 3. **轮换判定的配对键是 `(subject_der_sha256, spki_sha256)`**，不是 subject 显示串——
>    两个不同的 `Name` 可以渲染出同一个字符串。
> 4. **`--top` 只裁 `expiries[]`**，`summary.expiries_total` 与 `expiries_shown` 分开写，
>    好让"裁了多少"在纸面上可读；`findings` 与退出码不受影响。
> 5. **打码按路径形态判断**（盘符 / UNC / 正斜杠三类），**保留 basename**：
>    `<redacted>/server.pem`。整条抹成 `<redacted>` 会让诊断类 finding 不可执行——
>    "哪个文件"正是它唯一可执行的部分。打码施加在**成稿文档**上（两格式同一遍），
>    而不是挑字段打：新增一个带路径的字段默认就被遮住。
> 6. **退出码 1 只在这里产生**：`--fail-on` 缺省取策略 `report.default_fail_on`；
>    `none` 关的是门禁不是报告（findings 照常输出）。`--fail-on WARN` 表示"ERROR 或 WARN 都算达到门槛"。

## ⑤ 容器视图 `containers`

### 输入 / 输出

```
certledger containers <path>... [--show-aliases] [--password-env <VAR>] [--json <path>]
```

输出 alias 表：`alias` / `entry_type`（`PrivateKeyEntry` / `trustedCertEntry` / `SecretKeyEntry`）/
`fingerprint_sha256` / `chain_length` / `same_fingerprint_aliases[]`；
容器级信号：`CONTAINER_TRUSTSTORE_WITH_KEY` / `CONTAINER_EMPTY_PASSWORD` / `CONTAINER_UNREADABLE`。

### 实现路线

- PKCS#12：`cryptography.hazmat.primitives.serialization.pkcs12.load_key_and_certificates`。
- JKS / JCEKS：`keytool -list -v -keystore <path> [-storepass <pass>]`，**按 `Alias name:` /
  `Entry type:` 等键取值**，不依赖列宽与本地化排版（`LC_ALL=C` 环境）。
- `keytool` 缺失或非零退出 → `CONTAINER_UNREADABLE`（含 stderr 首行，**口令不得出现在 detail 里**）。

### 纪律

- 条目顺序按 alias 排序；
- 口令只从 `--password-env` 读；**不进 args**（ps 可见）、**不落盘**、**不进报告**；
- 子进程超时 20s，超时 → `CONTAINER_UNREADABLE`（`reason=timeout`）。

> **M5 实测补齐（2026-10-21）**——原文未写、但会改变结论的五点：
>
> 1. **口令的变量名有默认值**：`--password-env <VAR>` 改的是**变量名**，缺省为
>    `CERTLEDGER_CONTAINER_PASSWORD`（`inventory`/`hygiene`/`report` 没有这个参数，
>    它们读同名变量）。除用户给的口令外**只额外试空口令**（`b""` 与 `None` 两种写法），
>    代码里没有产品默认口令、没有字典。
> 2. **`keytool` 用 `-storepass:env <VAR>`**：口令走子进程环境，`argv` 里只有变量名。
>    JDK 9+ 支持；本机 JDK 26 实测。若 JDK 太老不支持，退化为 `CONTAINER_UNREADABLE`（不静默）。
> 3. **`LC_ALL=C` 不切换 JVM 语言**（本机实测输出仍是中文）。因此解析**按标签名**取值，
>    英文（`Alias name:` / `Entry type:` / `Certificate chain length:`）与中文（`别名:` /
>    `条目类型:` / `证书链长度:`）都认；并额外请求 `-J-Duser.language=en -J-Dfile.encoding=UTF-8`。
>    列宽与排版一概不依赖。
> 4. **`find_keytool` 的顺序**：`CERTLEDGER_KEYTOOL` → `PATH` → `JAVA_HOME` → JDK 安装根。
>    本机 `keytool` 不在 `PATH` 上（实测在 `C:\Program Files\Java\latest\jdk-26in\keytool.exe`）。
> 5. **`entries[]` 比原表多两列**：除 `alias` / `entry_type` / `chain_length` /
>    `same_fingerprint_aliases[]` 外，另给 `fingerprint_sha256` 与 `spki_sha256`，
>    使台账 `containers[]` 段自描述，并让容器条目能与 `certs[]`/`keys[]` 直接交叉核对
>    （`entries[].fingerprint_sha256` 是**证书 DER 的哈希**，与 `certs[]` 同一空间）。
>    **PKCS#12 的 `chain_length` 恒为 0**：bag 结构不区分链成员与外来可信证书，
>    把额外证书数当链长正是 `keytool` 在 `truststore-with-key` 上犯的错。
>    JKS 的 `chain_length` 取 `keytool` 的 `Certificate chain length`。

## ⑥ 失败路径总表（一物一码，报告里必须可检索）

| code | 何时 | 级别 | 是否改变退出码 |
|---|---|---|---|
| `SKIP_BINARY` / `SKIP_PERMISSION_DENIED` / `SKIP_TOO_LARGE` / `SKIP_SYMLINK` / `SKIP_UNKNOWN_FORMAT` | 采集期 | INFO | 否 |
| `SOURCE_UNAVAILABLE` | 后端缺失（含 macOS 未实测） | INFO | 否（D11） |
| `PARSE_FAILED` | 结构损坏（`stage` 指到 der/base64/pem） | WARN | 否 |
| `PARSE_UNSUPPORTED` | 识别为已知格式但当前版本不支持（如 PKCS#7、加密 OpenSSH） | INFO | 否 |
| `CONTAINER_UNREADABLE` | keytool 缺失/超时/非零退出 | WARN | 否 |
| `CONTAINER_FORMAT_AMBIGUOUS` | ~~JKS/JCEKS 魔数相同~~ **不适用**：两者魔数不同（`feedfeed` / `cececece`，JDK 26 实测），字节即可区分。该码保留在表中备将来真正歧义的容器格式，M2 不产出 | INFO | 否 |
| `POLICY_INVALID` | 策略缺字段/类型错/阈值无出处 | ERROR | **是 → 2** |

> "没看"与"没有"必须在报告里可区分：`summary.scanned` / `summary.skipped` / `summary.unavailable`
> 三个计数分别给出，且 `scanned + skipped` 与遍历到的文件数写进结论（有测试断言）。
